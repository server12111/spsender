# Устройство и границы надёжности

## Хранение

SQLite с foreign_keys=ON, WAL, synchronous=FULL и busy_timeout=30 секунд. Миграции `001_initial`, `002_ui_receipts`, `003_template_cursor`, `004_reliability` применяются по порядку в транзакциях; повторный запуск безопасен. Схема доступна в `app/db/migrations`. Вся долговременная бизнес-информация находится в БД; клиентские соединения и незавершённый ввод Telegram-login — временные ресурсы.

Основные сущности: admins, accounts, account_sessions, account_onboarding_events, campaigns, campaign_members, pairs, chat_pool, pair_chats, account_chat_access, campaign_templates, dispatch_jobs, message_attempts, message_results, greeting_progress, incoming_events, reply_history, chat_failures, chat_issues, chat_issue_decisions, notifications_outbox, audit_events, settings. greeting_templates / autoresponder_templates представлены SQL views над версионированными общими шаблонами.

Удаления логические: история сообщений, ошибок и решений сохраняется. При удалении аккаунта удаляется зашифрованная сессия, второй участник остаётся в неполной паре. Действие откладывается при INFLIGHT/UNKNOWN: сначала необходимо получить или сверить результат.

## Пары и время

Пара принадлежит одной кампании. Единственный `pair_chats` хранит общий список целей, last_sent_at и cooldown. Глобальный частичный UNIQUE по chat_pool_id не допускает параллельного назначения разным парам. Публикации возможны только в разрешённых чатах, с проверенными правами, своей сменой и готовыми обоими участниками; ограничение одного аккаунта не передаёт его окно другому.

День включения считается от первого допуска к заданию рассылки, а не от добавления аккаунта. `active_since` и `active_dispatch_seconds` сохраняются; остановка/пауза фиксирует накопленное время. Запущенная кампания после рестарта продолжает сохранённый интервал. Доля вычисляется от фактического набора, округляется вниз с минимумом 1 и не превосходит N. Стабильный порядок — ID назначения.

Первые 24 часа фоновых действий от аккаунта нет. Затем проверяется соединение; после 25 часов последовательно проверяются/выполняются одобренные подключения с минимальной паузой 50–100 секунд. При большом N этап продолжается дольше условного окна. От 26 часов выполняется разрешённое приветствие; до завершения подготовки и 27 часов готовность не выставляется. Добавление собственных аккаунтов в контакты необязательно и не используется: подготовка не требует внешних контактов или искусственной переписки.

## Очередь

1. Планировщик формирует задания с UNIQUE idempotency_key: для рассылок campaign/pair/chat/slot/version; для подготовки и приветствий устойчивый ключ конкретного шага.
2. BEGIN IMMEDIATE сериализует короткую операцию claim разных воркеров. UNIQUE-индексы дополнительно исключают два INFLIGHT по аккаунту либо паре+чату. Сетевые вызовы не держат транзакцию SQLite.
3. Перед внешним действием и после ожидавшей проверки прав Telethon повторно проверяет текущее состояние. Остановка между проверкой прав и отправкой отменяет отправку.
4. Успех Telegram записывается одной транзакцией: result, attempt, job, cooldown и выполненный шаг приветствия. Метрика успеха не растёт при постановке задачи или попытке.
5. Явный FloodWait ставит отложенное ожидание; ошибка аккаунта изолируется от ошибок чатов. Неизвестный сетевой исход и потерянный воркер дают UNKNOWN, блокируя дальнейшие действия до ручной сверки.

Между удалённым Telegram API и локальной SQLite нет общей распределённой транзакции. Поэтому абсолютное exactly-once при аварии не обещается. Безопасное поведение — не делать слепой повтор и требовать сверку UNKNOWN. Lease задания 180 секунд, timeout RPC 120 секунд. Отдельный runtime lease исключает одновременное владение MTProto-сессиями двумя живыми процессами. Heartbeat каждые 10 секунд поддерживает его во время сетевых ожиданий.

## Приветствия и ответы

Прогресс приветствия общий для campaign+chat и не сбрасывается при смене A/B. Три флага сохраняются отдельно; первоначальное и настраиваемое приветствие используют один механизм. По умолчанию все три части объединены. Раздельный формат требует двух разрешений: настройки кампании и правила чата. Для объединения резервируется 64 UTF-16 единицы поверх основного текста.

Триггеры автоответов соответствуют базовым старым функциям: входящее ЛС (однократный первый / каждый с cooldown), reply на сообщение подключённого аккаунта в группе. Свои аккаунты, исходящие и боты отфильтрованы. Входящее событие дедуплицируется, история срабатываний и резервирование задания хранятся в БД. Ручной ответ на уведомление допускается только для реального сохранённого входящего ЛС и в 10-минутное окно.

## Уведомления

Критические события создают приоритетный outbox в той же транзакции, которая приостанавливает аккаунт. Обычные проблемы формируют один агрегат не чаще 3600 секунд; повторные сводки сохраняют стабильные номера нерешённых проблем. «Оставить» исключает проблему из новых сводок, но сохраняет паузу. «Убрать» атомарно архивирует назначение и заполняет дефицит из общего пула в стабильном FIFO-порядке. Повторное решение не создаёт вторую замену.

Уведомления доставляются отдельно от отправок кампании. При сбое Bot API применяется backoff; outbox не теряется после рестарта. Доставка уведомлений администратору имеет семантику at-least-once: при сбое между ответом Bot API и фиксацией SENT возможно повторное административное уведомление. Повторное нажатие на решение всё равно идемпотентно.

## Доступ и эксплуатационные ограничения

Все входящие сообщения/callback проверяют ADMIN_IDS на сервере, интерфейс доступен только в личном чате. Кнопки имеют случайные токены, привязку к администратору, TTL, одноразовость для изменений и проверку версии настроек там, где нужна защита от устаревшего редактирования. Повторные сообщения администратора дедуплицируются. Коды/пароли не сохраняются; их сообщения удаляются по возможности. Библиотечные ошибки журналируются по классу/коду, без текста сессии или секретов.

SQLite рассчитана на один хост с локальным диском. Распределённый кластер и расширенная платформа резервного копирования не входят в согласованный объём. Для обычной файловой копии БД остановите приложение, чтобы не потерять данные WAL. Облачные GitHub Actions и реальный сервер Pterodactyl локально не запускались.
