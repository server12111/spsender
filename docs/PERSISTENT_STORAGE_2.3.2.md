# Хранение после пересборки — 2.3.2

21 ноября 2026. По уточнению владельца восстанавливать прежние данные не требуется. Восстановление, копирование старой базы и новые команды восстановления в выпуск не включены. Бот при разработке не запускался, рабочие данные и ключи не менялись.

## Что показал сервер

В предоставленном выводе Python: `DATA_DIR=None`, `DATABASE_PATH=/app/data/fe_autosender.sqlite3`, `MODE=live`, количество аккаунтов и рассылок — `0, 0`. В `/app/data` есть база, каталог `/srv/fe-autosender/data` пуст. Владелец сообщил, что данные исчезли после пересборки и ключ не менял.

Следовательно, путь уже находился в правильной папке. Простое повторное указание того же DATABASE_PATH не устраняет ошибки подключения хранилища. В Dockerfile обнаружена директива `VOLUME /app/data`, способная создавать отдельный анонимный том, когда платформа подключает родительскую папку `/app`. Анонимные тома автоматически не переносятся между новыми контейнерами. Это обнаруженный риск конфигурации; фактические Docker mount-данные серверного контейнера не проверялись, поэтому единственную причину прошлой потери данных не утверждаем.

Основания: [Bothost о сохранении данных при пересборке](https://bothost.ru/docs/sqlite-data-lost), [Bothost о bind mount на /app](https://bothost.ru/docs/common-errors), [Docker об анонимных томах](https://docs.docker.com/engine/storage/volumes/).

## Что исправлено

- Убрана директива `VOLUME` из Dockerfile. Постоянный том предоставляет Bothost; локальный Compose подключает именованный `autosender_data:/app/data`. Имя существующего Compose-тома сохранено.
- В Docker задан `DATA_DIR=/app/data`. Путь Compose совпадает с Bothost. Код образа остаётся отдельно, в `/srv/fe-autosender`.
- По последнему уточнению владельца для сервера оставлен **только DATA_DIR**. Имя файла `fe_autosender.sqlite3` задано в коде. При указанном DATA_DIR прежний DATABASE_PATH не влияет на выбор файла — даже если там осталась папка или другой путь.
- Если DATA_DIR отсутствует, на Linux используется существующая папка `/app/data`; локальное поведение Windows сохраняется.
- Перед запуском live-процесса в Docker проверяется Linux mountinfo: база должна находиться на внешнем монтировании. Поддерживается как родительский bind `/app`, так и отдельный том `/app/data`. Слой контейнера и tmpfs/ramfs не принимаются. Проверка не может определить, сохранит ли провайдер свой том в будущем, но предотвращает тихую работу без внешнего хранилища.
- В журнале старта выводятся абсолютный путь базы и точка монтирования, без токенов и ключей.
- SESSION_KEY проверяется до создания/миграции базы. Новый ключ при старте или пересборке не генерируется.

## Что указать в окружении Bothost

```dotenv
DATA_DIR=/app/data
```

Удалите DATABASE_PATH из переменных сервера. MODE оставьте `live`; сохраните прежние `SESSION_KEY`, `BOT_TOKEN`, `ADMIN_IDS` и API-реквизиты. Готовый шаблон — [.env.hosting.example](../.env.hosting.example). После обновления кода нужна одна пересборка/перезапуск. Добавление аккаунта/рассылки и повторная пересборка на самом Bothost владельцем подтвердят работу конкретного серверного тома.

Если новая версия останавливается с сообщением о постоянном томе, на стороне хостинга не подключено внешнее хранилище. Оно должно быть подключено к `/app/data` либо родительской `/app` согласно документации Bothost. Добавление одной переменной окружения само по себе не создаёт постоянный том.

## Проверки

[test_storage.py](../tests/test_storage.py) моделирует новый каталог образа при сохранённом каталоге данных: аккаунт, шифротекст сессии и созданная рассылка сохраняются. Проверены приоритет единственного DATA_DIR перед устаревшим DATABASE_PATH, допустимые bind/named mounts, отказ без тома и в tmpfs, отсутствие базы при ошибке ключа и конфигурация Docker/Compose. Также проверены отказ при указании папки вместо файла и диагностическая заметка с точным путём при SQLITE_CANTOPEN — без изменения исходного кода SQLite-ошибки.

В полном прогоне обнаружен нестабильный существующий тест перегрузки входящих: он ждал записи уведомления только 80 мс. Ожидание заменено событием после фиксации транзакции с тайм-аутом 10 с; производственный обработчик не менялся.

Полный результат: **491 passed за 89,23 с**, [JUnit XML](storage-test-results.xml), включая 19 новых случаев. Ruff и smoke прошли. Проверена установка wheel: фиксированное имя базы при DATA_DIR, сохранение аккаунтов, рассылки и файлов после смены папки кода, схема 013. Docker CLI в рабочем окружении отсутствует, реальная сборка Docker и пересборка на Bothost не выполнялись. Настоящие сообщения и авторизации не отправлялись. Миграции для исправления путей не нужны.
