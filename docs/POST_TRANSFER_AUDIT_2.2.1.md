# Проверка после переноса — 2.2.1

Дата: 3 ноября 2026. Проверена версия 2.2.0 после подключения исходного кода архива. Бот не запускался; Telegram API подменён. Исходный архив и рабочие `.env`, ключи, сессии и БД не изменялись.

## Найдено и исправлено

| Ошибка | Последствие | Исправление |
|---|---|---|
| Повторное вступление использовало контекст без `next_index` | `KeyError` до запроса вступления | В журнале отделены поля доставки от полей подготовительной операции |
| Подготовительный RPC мог включить часы рассылки пары | Время подготовки учитывалось как время отправки | Часы включаются только при передаче сообщения, не при вступлении |
| После приватного вступления исходный сервис передаёт объект чата | Адаптер искал строковое представление объекта и отклонял отправку | Назначение определяется по исходному снимку цели с проверкой принадлежности паре |
| Отложенная запись исходного сервиса повторно сохраняла курсор текста | Старый пакет мог откатить уже подтверждённый номер следующего шаблона | ACK единолично сохраняет курсор, интервал, счётчик и аккаунт отправки одной транзакцией; повторная запись удалена |
| Неудачное отключение при авторизации удаляло ссылку на клиент | Нельзя было повторить очистку; временные файлы/соединение оставались | Клиент сохраняется до успешного отключения; независимые ресурсы очищаются даже при ошибке одного из них |
| Исходный очиститель импорта скрывал ошибку отключения | Внешний код ошибочно считал источник закрытым | Ошибка передаётся вызывающему коду; повторная очистка сохраняет контроль над клиентом |
| Клиент импорта регистрировался только после подключения/проверки | При сетевой ошибке до возврата из функции клиент терялся | Источник и новая сессия регистрируются сразу после создания; повтор завершения использует существующий клиент |
| Время снимка прогрева назначалось в момент записи | Старый общий снимок мог перекрыть более свежие счётчики перед RPC | Версия назначается при наблюдении состояния; порядок строго возрастает и учитывает одинаковые тики часов Windows |
| Очистка старых диалогов не различала новые записи | Параллельно начатый диалог удалялся как отсутствующий в старом снимке | Удаляются только записи не новее снимка; кэш очищается после COMMIT |
| Отложенный снимок диалога перезаписывал новый шаг | После рестарта восстанавливалась устаревшая позиция | SQLite отклоняет старую версию; кэш учитывает порядок записей и общий для адаптеров одного Engine |
| Ответ `UserAlreadyParticipant` считался неопределённым исходом | Здоровый аккаунт блокировался, хотя уже состоял в чате | Для операций вступления это подтверждённый результат; пауза между вступлениями сохраняется |
| Подтверждённое вступление кэшировалось как вечное членство | После последующего выхода или удаления из чата новый запрос не выполнялся | Каждая разрешённая по времени попытка вступления получает запись журнала; неопределённые попытки по-прежнему блокируют аккаунт |

Первые восемь регрессионных тестов были запущены до исправлений: **все восемь упали по указанным причинам**. Затем добавлены проверки ранней регистрации клиентов, ошибок входа по номеру, повторного завершения импорта и известных исходов вступления. Файл: `tests/test_post_transfer_audit.py`, 15 тестов. Новые функции бота не добавлялись, исходные сценарии и интервалы прогрева сохранены.

## Предыдущая ошибка CI

В запуске [41654132462](https://github.com/server12111/spsender/actions/runs/41654132462) три комбинации ОС/Python прошли, Windows/Python 3.11 получил `1 failed, 313 passed`. Единственное падение — `test_critical_stop_button_is_not_blocked_by_long_admin_operation`: секундный предел истёк **при построении карточки после выполненной остановки**, а не при ожидании административной блокировки. Полный прогон на этом диске занял 566 секунд против примерно 50 секунд локально.

Проверка по-прежнему удерживает административную блокировку до завершения команды, поэтому ошибочный захват этой блокировки гарантированно выявляется. Увеличен только технический тайм-аут до 10 секунд для медленного диска CI; проверка фактического статуса `STOPPED` сохранена. Это исправление нестабильности теста, а не объявление продуктовой ошибки исправленной увеличением тайм-аута.

## Проверки и ограничения

Полный прогон: **329 passed за 54,80 с**, [post-transfer-test-results.xml](post-transfer-test-results.xml). Ruff и `python -m app smoke` также прошли. Внешние сокеты при тестах заблокированы; реальных отправок, вступлений и авторизаций нет. Отдельный нагрузочный прогон сохранён в `post-transfer-load-results.json`.

Повторная нагрузочная имитация: **1 000 аккаунтов, 10 000 чатов, 1 000 подтверждённых сообщений**, пересоздание runtime и соединения с SQLite посередине. Дублей **0**, нарушений внешних ключей **0**, `integrity_check=ok`. Время обработки **56,1432 с**, CPU **62,5469 с**, пик RSS **80,03 МБ**, максимальная задержка heartbeat **136,384 мс**. Фактическая параллельность отправок — не более **3** при лимите **4**. 100 000 проверок прогрева из снимка — **0,0635 с**. Это тест адаптеров, SQLite и пути отправки с подменённым API; тысяча настоящих Telegram-соединений не создавалась.

Первоначальное подозрение на автоответы между собственными аккаунтами **не подтвердилось**: общий обработчик уже исключает Telegram ID всех собственных аккаунтов. Эта защита сохранена.

Известные границы проверки: живое подключение Telegram, реальный tdata/QR-вход и длительная эксплуатация на тысячах настоящих соединений не проверялись. Неопределённый результат RPC по-прежнему блокируется для ручной сверки, автоматического повторения нет. Абсолютное отсутствие ошибок этими тестами не доказывается.
