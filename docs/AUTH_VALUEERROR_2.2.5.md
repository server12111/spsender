# ValueError при авторизации — 2.2.5

20 ноября 2026. Домен для входа аккаунта не нужен. Транспорт подключается к Telegram напрямую, интерфейс бота использует polling.

Полученные серверные строки `authorization-ui error=ValueError` и `UI-input error=DomainError` обозначают исходный сбой и преобразование его в сообщение интерфейса. Причина самого `ValueError` и место возникновения в них отсутствуют. Ошибка сервера с настоящим аккаунтом локально не воспроизводилась; утверждать, что причиной были API-реквизиты или библиотека, оснований пока нет.

В 2.2.5 добавлено:

- `authorization-step`: класс исключения, этап (`create_client`, `connect`, `request_code`, `cleanup_previous`, ввод кода/пароля), список `файл:функция:строка`, версии Telethon и opentele-ng. Не записываются текст исключения, RPC-запрос, строки исходника, локальные переменные, номера, коды, пароли или API hash.
- `api_id=` и `api_hash=` передаются именованными параметрами, чтобы исключить неоднозначность позиции `api` в расширенном конструкторе opentele. Реальное создание клиента без подключения проверено с opentele-ng 1.4.0 и локальной 1.5.0. На обеих версиях предыдущий вызов тоже работал: это дополнительная защита совместимости, не доказанная причина серверного сбоя.
- Подтверждённый отдельный баг исправлен: ошибка отключения после неудачного запроса кода больше не подменяет исходную ошибку. Неотключённый клиент сохраняется для повторной очистки; обе ошибки диагностируются раздельно.

Новые проверки: [test_auth_valueerror.py](../tests/test_auth_valueerror.py), шесть случаев. До исправлений все шесть воспроизводили недостающую диагностику, неоднозначное позиционное связывание в тестовом расширенном конструкторе и подмену ошибки при отключении. Telegram API подменён, настоящие запросы кодов не выполнялись.

Полный результат: **431 passed за 65,89 с**, [JUnit XML](auth-valueerror-test-results.xml). Ruff и smoke прошли. Рабочие `.env`, база, сессии и журналы не изменялись, бот не запускался.

После обновления кода на сервере нужен перезапуск процесса/пересборка контейнера. Если вход снова завершится ошибкой, строка `authorization-step` даст место сбоя и этап. Повторять запросы кодов подряд не нужно; сохранение FloodWait и паузы 2.2.4 остаются действующими. Доставка кода на реальном аккаунте этой проверкой не подтверждена.
