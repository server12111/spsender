Автоподписки по явным требованиям доверенных ботов группы; CAPTCHA — вручную. Ссылки на Telegram-пиры сохраняются зашифрованно для восстановления после рестарта. [Логика, запуск и проверки](docs/WEEKLY_ROTATION.md).

**2.0.6:** исправлены входящие сообщения, восстановление ЛС, перенос и повторное добавление аккаунтов, права вступления, кнопки, сохранение мастера и сетевые ожидания. Добавлена миграция 007 для существующих SQLite-баз. [Отчёт проверки и изменения](docs/AUDIT_FIXES_2.0.6.md).

**2.0.5:** доступ к управлению — только ID из `ADMIN_IDS` и только в личном чате. В `.env.example` список пуст: укажите свой числовой Telegram ID; без него бот не запустится. Добавлены совместимый `main.py` и Docker-запуск. [Проверка доступа перед публикацией](docs/ADMIN_RELEASE.md).

**2.0.4:** первое входящее ЛС → стикер → короткое приветствие → основной текст. Паузы между частями 3–4 с сохраняются в SQLite. Добавлен стандартный статус «печатает…» перед отправками аккаунтов. [Поведение и проверки](docs/TYPING_AND_DM.md).

Обновление **2.0.3**: отдельный экран автоматической подготовки, облегчённый список аккаунтов и выбор только свободных аккаунтов для рассылки. [Последняя проверка](docs/UI_REVIEW.md). Кнопки по две в ряд, меню обновляется в одном сообщении. [Изменения интерфейса 2.0.2](docs/UI_NOTES.md).

Отдельный личный Python-проект с Telegram-админкой на русском языке. **По уточнению владельца используется SQLite, без PostgreSQL и без отдельного сервера БД.** Исходный архив не изменялся и не запускался.

Реализованы кампании, собственные аккаунты, общий пул разрешённых групп/каналов и тем, пары A/B, фиксированные смены, индивидуальная подготовка, очередь, приветствия, базовые автоответы, уведомления и статистика. [Аудит исходника](docs/AUDIT.md), [отчёт и 27 проверок](docs/ACCEPTANCE.md), [архитектура](docs/ARCHITECTURE.md), [исходное ТЗ](docs/SPECIFICATION.md).

## Требования

- Код рассчитан на Python 3.11+. Локальная проверка выполнена на Windows и Python 3.11.0; матрица CI проверяет Linux/Windows, Python 3.11/3.13.
- Локальный постоянный диск для SQLite. Не размещайте работающую базу на SMB/NFS или в синхронизируемой облачной папке. Один процесс `run` обслуживает бота и аккаунты; второй живой runtime блокируется lease.
- Для интерфейса нужны свой BOT_TOKEN и числовые ADMIN_IDS. Для реальных аккаунтов также нужны собственные TELEGRAM_API_ID / TELEGRAM_API_HASH.
- Тесты и `smoke` не требуют Telegram, токенов или настоящих аккаунтов.

## Windows / PowerShell

Откройте терминал в папке `fe_autosender_2`:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m app smoke
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m app keygen
```

Если установлен только Python 3.11, замените `py -3.13` на `py -3.11`.

Вставьте выданный ключ в `SESSION_KEY` в `.env`. Задайте `BOT_TOKEN` и `ADMIN_IDS`. Оставьте `MODE=dry-run` для знакомства с интерфейсом. Затем:

```powershell
.\.venv\Scripts\python.exe -m app migrate
.\.venv\Scripts\python.exe -m app check
.\.venv\Scripts\python.exe -m app run
```

Напишите своему боту `/start` в **личном** чате. Всё дальнейшее управление — кнопками. В dry-run для добавления фиктивного аккаунта используется код `00000`.

Файл `.env` и папка `data` должны быть доступны только владельцу приложения и системному администратору. На Windows проверьте «Свойства → Безопасность» у этих объектов; не предоставляйте доступ группе «Все». На Linux приложение создаёт каталог БД с правами 700 и файл БД с правами 600. Не публикуйте `.env`, ключ или файлы БД.

## Docker

Создайте `.env` по примеру, заполните `BOT_TOKEN`, `ADMIN_IDS` и `SESSION_KEY`. Для реальных аккаунтов также нужны `TELEGRAM_API_ID` и `TELEGRAM_API_HASH`; для первого знакомства оставьте `MODE=dry-run`.

```bash
docker compose up -d --build
docker compose logs -f bot
docker compose stop
```

SQLite, медиа и журналы хранятся в отдельном постоянном томе `autosender_data`. Секреты поступают через `.env`, в образ они не копируются. Контейнер работает от непривилегированного пользователя; штатная остановка использует SIGINT. Docker-сборка локально не выполнялась — автоматические проверки Python описаны в отчёте.

Для хостинга с командой `python main.py` совместимый запускатель стартует тот же бот. Команда `python main.py check` выполняет только проверку SQLite и конфигурации. Новый бот использует собственную БД; старые базы другого приложения автоматически не преобразуются.

Для воспроизводимого набора зависимостей есть `requirements.lock`: установите его, затем `pip install --no-deps -e .`. Это снимок окружения, в котором выполнены локальные тесты. Обычный `pip install -e '.[test]'` использует совместимые диапазоны из `pyproject.toml`.

## Pterodactyl

1. Выберите Python egg / образ Python 3.13 и постоянный том для папки приложения.
2. Загрузите исходники нового проекта без `.venv`, без старого архива и без `.audit`.
3. Установите зависимости командой `python -m pip install -e .` (или настройте её как install-команду egg).
4. Создайте `.env` по примеру либо задайте переменные окружения панели. `DATABASE_PATH` должен указывать на постоянный локальный том, например `/home/container/data/fe_autosender.sqlite3`.
5. В консоли выполните `python -m app migrate`, затем `python -m app check`.
6. Startup command: `python -m app run`. Не запускайте дополнительный `worker` одновременно с `run`: `run` уже содержит воркер и доставку уведомлений.
7. Останавливайте процесс штатно. При аварийном завершении INFLIGHT-задания после истечения 180 секунд перейдут в «Результат неизвестен» для ручной сверки.

Для отдельного фонового режима существует `python -m app worker`: он обслуживает очередь и уведомления без polling интерфейса. Это альтернативный режим того же процесса, а не обязательный второй сервис.

## Первый рабочий сценарий

1. «Рассылки → Создать»: название, несколько текстов и необязательные вложения, интервал, свободные аккаунты, N общих чатов на пару, переключатели функций, предпросмотр и сохранение.
2. «Аккаунты → Добавить»: название, собственный номер, код Telegram и при необходимости пароль 2FA. Если кампания одна, назначение автоматическое; если несколько — выбор кнопками; если нет — свободный пул. Новые аккаунты автоматически объединяются в неполные пары по порядку. Есть отдельное связывание свободных участников одной кампании.
3. «Пул чатов → Импорт»: ID, `ID:topic_id`, @username, t.me-ссылки либо TXT UTF-8. До 1000 строк за импорт. Дедупликация по фактическому Telegram ID + теме. Подтвердите право публикации и правила приветствий/вступления.
4. Чаты распределяются автоматически в порядке добавления. N=20 — **20 общих чатов для A+B**, а не 40. Дефицит и замены обрабатываются очередью.
5. В карточке кампании настройте общие приветствия и автоответы, если они нужны. Включённая функция без текста не отправляет пустые сообщения.
6. Нажмите «Запустить» и подтвердите. Первые 24 часа каждого нового аккаунта внешних фоновых действий нет. После подключения и подготовки обоих участников пара допускается к публикациям в своих сменах.

Часовой пояс задаётся один раз в «Настройках», по умолчанию Europe/Kyiv. A: 00–06 и 12–18, B: 06–12 и 18–00. Время хранится в UTC; при сменах cooldown и история не сбрасываются. Активная доля закреплённых чатов: 10% → 30% → 60% → 100% по 24 часа активного времени пары. Явная пауза кампании и ограничения пары останавливают этот счётчик. Работающий сервер после перезапуска продолжает сохранённые интервалы; перезапуск сам по себе не сбрасывает день.

## Режимы и реальные отправки

`MODE=dry-run` использует FakeTransport: обращения к аккаунтам, вступления и публикации в целевых чатах отсутствуют. При `run` бот всё равно использует Bot API для интерфейса и сообщений самому администратору. Полностью без сети работают `smoke` и тесты; в тестах Bot API тоже подменён.

Для реальной эксплуатации остановите приложение, задайте `MODE=live`, собственные API credentials и **новый DATABASE_PATH**, например `data/live.sqlite3`. Тестовую базу с фиктивными аккаунтами нельзя переключить в live: предусмотрен запрет смешивания режимов. Добавьте реальные собственные аккаунты через интерфейс и импортируйте разрешённые цели. Запуск кампании требует отдельного подтверждения кнопкой.

Приложение при разработке не подключалось к настоящим аккаунтам и не запускало реальные рассылки. Проверить настоящий login/2FA, отрисовку Telegram-клиентов и фактические права конкретных групп сможет владелец на своём токене.

## Ошибки и восстановление

- Временная ошибка A запрещает повторять её тем же аккаунтом; B может проверить доступ в собственной смене. Явный запрет публикации ставит чат на паузу сразу. Два независимых сбоя A/B также открывают проблему. Запрет не обходится сменой аккаунта.
- Нерешённые проблемы поступают одной общей нумерованной сводкой не чаще раза за 3600 секунд. Для длинных списков есть страницы. Номер проблемы стабилен и совпадает с кнопками.
- «Убрать» архивирует проблемное назначение и автоматически берёт первую подходящую замену. Если её нет, добавление нового разрешённого чата автоматически закрывает дефицит. «Оставить» сохраняет принадлежность и паузу; возобновление — отдельное подтверждение в карточке чата после проверки.
- FROZEN / SESSION_EXPIRED / RESTRICTED: аккаунт приостановлен, критический outbox создаётся сразу. Доставка запускается сразу после ошибки и независимо проверяется каждую секунду. При недоступности Bot API уведомление остаётся в повторной очереди. FloodWait — отдельное временное ожидание, оно не объявляется спамблоком.
- «Результат неизвестен»: сначала вручную сверьте Telegram. Затем в «Ошибки → Неизвестные результаты» подтвердите, была ли операция выполнена. Неизвестный запрос автоматически не повторяется. Уже подтверждённые отправки не переотправляются после рестарта.
- CAPTCHA, опрос на допуск и проверка «Я не робот» требуют ручного прохождения. Бот не нажимает защитные кнопки и не голосует.
- «Остановить рассылку» отменяет будущие сообщения, автоответы, приветствия и подключения этой кампании. Уже отправленный сетевой запрос учитывается по его результату. Статистика сохраняется.

## Структура

```text
app/bot/              русский интерфейс, мастера и aiogram
app/services/         аккаунты, пары, кампании, чаты, подготовка,
                      рассылки, приветствия, ответы, уведомления, статистика
app/db/migrations/    нумерованные транзакционные SQL-миграции SQLite
app/scheduler/        очередь и lease живого runtime
app/security/         шифрование сессий и ограничение логов
app/transport/        настоящий Telethon и полностью локальные подмены
app/data/             30 эмодзи и 100 фраз из ТЗ
tests/                приёмочные, интеграционные и отказные проверки
docs/                 аудит, архитектура, приёмка и ТЗ
```

Статистика доступна внутри Telegram: общая, по аккаунту, паре, чату, кампании и ошибкам; сегодня, вчера, 7/30 дней и всё время. «Подтверждено» означает подтверждение API либо явную ручную сверку неопределённого результата. Метрик прочтений нет. Платежи, платные подписки сервиса, рефералы и экспорт CSV/Excel не включены. По последнему уточнению владельца в 2.2.0 включён исходный прогрев с диалогами собственных аккаунтов; прежнее исключение из исходного ТЗ в этой части заменено этим уточнением.

Используемые интерфейсы библиотек сверены с [документацией aiogram](https://docs.aiogram.dev/en/latest/dispatcher/finite_state_machine/index.html) и [Telethon](https://docs.telethon.dev/en/stable/modules/client.html). Мастера сохраняют состояние в SQLite, чтобы обычный перезапуск не сбрасывал введённые настройки; незавершённый интерактивный Telegram-login после перезапуска нужно начать заново, коды и пароли не сохраняются.
